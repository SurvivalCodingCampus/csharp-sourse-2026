## 0. 시작하기 전에

### 완성할 앱

| 항목 | 내용 |
|---|---|
| 앱 | 키워드로 이미지를 검색해 결과를 그리드로 보여주는 모바일(세로) 앱 |
| 데이터 | 처음엔 Mock 데이터 → 마지막에 [Pixabay API](https://pixabay.com/api/docs/) |
| 구조 | Model / DTO / Mapper / DataSource / Repository / Result 패턴 (+ 필요하면 Service) |
| 검증 | EditMode Unit Test + PlayMode Test |

### 전체 흐름

```
설치(CLI, Skills) → 프로젝트 생성·커밋 → 규칙 파일
→ 디자인 분석 → PlantUML 설계 → 설계 보강
→ 테스트 시나리오 → Mock 기반 코드·테스트 → Unit Test 통과
→ UI 작성 → UI·데이터 연결 → PlayMode 시나리오 → PlayMode 테스트
→ 실제 API(Pixabay) 연결
```

각 단계는 **프롬프트 → 에이전트 작업 → 검토 포인트 확인 → 커밋**의 반복입니다.

### 사전 지식

이 교재에서 **모두 사용**하는 개념입니다. 처음 보는 개념이 있다면 [부록 B](#부록-b-개념이-쓰이는-곳-한눈에-보기)에서 어느 단계에 쓰이는지 먼저 확인하세요.

- 객체지향 (캡슐화, 추상화, 다형성)
- SOLID 원칙
- 테스트 코드 (Unit Test, Mock)
- DataSource, Model, Repository, DTO, Mapper
- Result 패턴
- PlantUML 클래스 다이어그램

### 준비물

| 준비물 | 용도 |
|---|---|
| Unity 계정 (Personal 가능) | 로그인·라이선스 |
| Git | 버전 관리 |
| Node.js (LTS) | `npx`로 Unity Skills 설치 |
| AI 코딩 에이전트 1개 | Claude Code, Codex, Antigravity 등 무엇이든 |
| PlantUML 뷰어 | IDE 플러그인(JetBrains / VS Code) 또는 [plantuml.com](https://www.plantuml.com/plantuml) |

### 어떤 에이전트를 써도 되는 이유

이 교재의 프롬프트는 **특정 제품의 명령어를 쓰지 않고 자연어**로 작성되어 있습니다.

- **CLI 모드든 데스크톱 앱이든** 프롬프트는 같습니다. 에이전트가 터미널 명령을 실행하고 파일을 편집할 수 있기만 하면 됩니다.
- **스킬은 자동으로 선택**됩니다. 에이전트가 요청 내용을 보고 알맞은 Unity 스킬을 고릅니다. 확실히 하고 싶으면 프롬프트에 `unity-cli 스킬을 사용해서`처럼 **스킬 이름을 적어 주세요.**
- **스크린샷 첨부**는 도구마다 방법이 다릅니다(붙여넣기, 드래그, 파일 경로 입력). 이미지를 받을 수 없는 환경이면 파일로 저장한 뒤 경로를 알려 주세요.

### 에이전트와 일하는 5가지 원칙

1. **한 번에 한 단계만** 요청합니다. "전부 다 만들어 줘"는 검토할 수 없는 결과를 만듭니다.
2. **계획 먼저, 실행은 승인 후.** 큰 작업은 "먼저 계획만 보여줘"로 시작합니다.
3. **완료 조건을 명시**합니다. "테스트가 모두 통과하고 컴파일 에러가 없을 것"처럼 확인 가능한 기준을 줍니다.
4. **증거로 보고받습니다.** "됐습니다"가 아니라 테스트 결과 요약, 스크린샷, `git status`를 요구합니다.
5. **단계마다 커밋**합니다. 잘못되면 되돌릴 지점이 생깁니다.

> 💡 이 교재의 프롬프트는 그대로 복사해 써도 되지만, `〈 〉`로 표시된 부분은 여러분의 상황에 맞게 바꾸세요.

## 1. Unity CLI 설치

Unity CLI는 에디터 설치, 프로젝트 생성, 빌드·테스트, **실행 중인 에디터 제어**까지 터미널에서 할 수 있게 해 주는 단일 실행 파일입니다. 출력이 JSON으로 구조화되어 있어 AI 에이전트가 결과를 정확히 읽을 수 있습니다. (참고: [Unity CLI 소개 블로그](https://unity.com/kr/blog/meet-the-unity-cli))

> ⚠️ Unity CLI는 현재 **베타**이며 **Unity 6.0 LTS 이상**에서 동작합니다.

### 1-1. 설치

**macOS / Linux**

```bash
curl -fsSL https://public-cdn.cloud.unity3d.com/hub/prod/cli/install.sh | UNITY_CLI_CHANNEL=beta bash
```

**Windows (PowerShell)**

```powershell
$env:UNITY_CLI_CHANNEL='beta'; irm https://public-cdn.cloud.unity3d.com/hub/prod/cli/install.ps1 | iex
```

설치 후 **터미널을 새로 열고** 확인합니다.

```bash
unity --version
unity --help
```

### 1-2. 로그인과 라이선스

```bash
unity auth login                       # 브라우저로 Unity 계정 로그인
unity auth status --format json        # "loggedIn": true 확인
unity license status --format json     # 활성 라이선스 확인
```

### 1-3. 에디터 확인

이미 Unity Hub로 설치한 에디터가 있다면 그대로 사용할 수 있습니다.

```bash
unity editors --format json            # 설치된 에디터 목록
```

에디터가 없다면 지금 설치하지 않아도 됩니다. 3단계에서 에이전트가 설치해 줍니다.

### ✅ 검토 포인트

- [ ] `unity --version`이 버전을 출력한다
- [ ] `unity auth status`에서 로그인 상태가 `true`다
- [ ] `unity license status`에 활성 라이선스가 있다

## 2. Unity Skills 설치

**스킬(Skill)** 은 에이전트에게 주는 "작업 설명서"입니다. `SKILL.md` 파일에 특정 작업을 어떤 순서로, 어떤 명령으로, 무엇을 조심하며 해야 하는지가 적혀 있고, 에이전트는 요청에 맞는 스킬을 골라 그대로 따릅니다. [Unity-Technologies/skills](https://github.com/Unity-Technologies/skills)는 Unity가 공식으로 제공하는 스킬 모음입니다.

### 2-1. 프로젝트 폴더 만들기

스킬은 **프로젝트 폴더 단위**로 설치하는 것을 권장합니다. 앱을 만들 빈 폴더를 먼저 만듭니다.

```bash
mkdir image-search
cd image-search
```

### 2-2. 설치

```bash
npx skills add Unity-Technologies/skills
```

설치 중에 다음을 묻습니다.

| 질문 | 선택 |
|---|---|
| 설치할 스킬 | 전체 설치 권장 |
| 사용할 에이전트 | 여러분이 쓰는 에이전트 (여러 개 선택 가능) |
| 범위(scope) | **Project** (이 폴더에만 설치) |

설치가 끝나면 이런 파일이 생깁니다.

```
image-search/
├── .agents/skills/…        ← 스킬 원본
├── .claude/skills/…        ← (선택한 에이전트별 폴더, 예시)
└── skills-lock.json        ← 설치된 스킬 목록과 버전
```

자주 쓰는 관리 명령입니다.

```bash
npx skills list                                  # 설치된 스킬 보기
npx skills add Unity-Technologies/skills --list  # 설치 가능한 스킬 보기
npx skills update                                # 최신 버전으로 갱신
```

### 2-3. 이 교재에서 쓰는 스킬

| 스킬 | 쓰이는 단계 |
|---|---|
| `new-unity-project` | 3. 프로젝트 생성 (질문 → 에디터 설치 → 프로젝트 → Git) |
| `unity-cli` | 전 단계 (에디터 제어, C# 실행, 테스트 실행) |
| `unity-package-management` | 8. 패키지 설치 (예: 비동기 라이브러리) |
| `ui`, `ui-ugui`, `ui-uitk` | 10. UI 작성 |

### 2-4. 에이전트 실행과 스킬 인식 확인

프로젝트 폴더에서 에이전트를 실행하고 첫 프롬프트를 보냅니다.

```text
이 폴더에 설치된 Unity 스킬 목록을 보여 주고, 각각 어떤 상황에서 쓰는지 한 줄씩 설명해 줘.
그리고 unity-cli 스킬을 사용해서 Unity CLI 버전, 로그인 상태, 라이선스 상태, 설치된 에디터를 확인해 줘.
```

### ✅ 검토 포인트

- [ ] 에이전트가 `new-unity-project`, `unity-cli` 등의 스킬을 알아본다
- [ ] 에이전트가 직접 `unity` 명령을 실행해 상태를 보고한다
- [ ] 스킬을 못 찾는다면: 에이전트를 **프로젝트 폴더에서** 실행했는지, 설치 때 그 에이전트를 선택했는지 확인한다

## 3. 에이전트 실행과 새 프로젝트 생성, 첫 커밋

### 3-1. 프로젝트 생성 요청

```text
new-unity-project 스킬을 사용해서 이 폴더에 새 Unity 프로젝트를 만들어 줘.

- 앱: 키워드로 이미지를 검색하고 결과를 그리드로 보여주는 모바일 앱
- 화면: 세로(Portrait) 모바일
- 게임 요소 없음, UI 중심 앱
- 이 폴더에는 이미 스킬 파일(.agents 등)이 있으니 지우지 말고 그 옆에 프로젝트를 구성해 줘

진행 전에 필요한 질문(플랫폼, 에디터 버전, 템플릿, 소스 관리 방식)을 먼저 해 줘.
```

에이전트는 스킬의 흐름에 따라 질문합니다. 예시 답변입니다.

| 질문 | 예시 답변 |
|---|---|
| 타깃 플랫폼 | 처음에는 에디터에서만 테스트 (Android/iOS 모듈은 나중에) |
| 에디터 버전 | 설치된 Unity 6 LTS, 없으면 최신 LTS |
| 템플릿 | URP 템플릿 (에이전트 추천을 들어 보고 결정) |
| 소스 관리 | 로컬 Git |

> 💡 에디터를 새로 설치해야 하면 수 분이 걸립니다. 스킬은 설치를 **백그라운드로** 돌리고 그동안 질문을 이어 가도록 되어 있습니다.

### 3-2. 기본 설정 확인

```text
프로젝트를 에디터로 열고 다음을 확인해서 표로 보고해 줘.
- 렌더 파이프라인과 사용한 템플릿
- 화면 방향(Portrait) 설정
- 설치된 패키지 목록
- 에디터를 CLI로 제어할 수 있는지 (unity status가 ready인지)
```

### 3-3. 첫 커밋

```text
첫 커밋을 해 줘.
커밋 전에 git status로 Library, Temp, Logs, UserSettings 같은 자동 생성 폴더가
제외되어 있는지 확인하고, 스테이징된 파일을 폴더별로 요약해서 보여 줘.
```

### ✅ 검토 포인트

- [ ] `.gitignore`가 있고 `Library/`, `Temp/` 등이 커밋에서 빠졌다
- [ ] `.cs`/에셋 파일과 `.meta` 파일이 함께 커밋되었다
- [ ] 템플릿이 URP 계열이다 (Built-in 템플릿은 새 프로젝트에 권장되지 않음)
- [ ] `unity status`로 에디터가 `ready` 상태로 보인다 (이후 단계에서 에디터 제어에 필요)

## 4. 에이전트 규칙 파일 만들기

에이전트는 대화가 바뀌면 이전 결정을 잊습니다. **규칙 파일**은 에이전트가 세션을 시작할 때마다 자동으로 읽는 프로젝트 지침서입니다.

| 에이전트 | 규칙 파일 (대표적인 이름) |
|---|---|
| 여러 에이전트 공통 | `AGENTS.md` |
| Claude Code | `CLAUDE.md` |
| Gemini 계열 (Antigravity 등) | `GEMINI.md` |

> 💡 여러 에이전트를 함께 쓴다면 내용은 `AGENTS.md` 하나에 쓰고, 다른 파일에서는 "AGENTS.md를 따른다"고만 적어 중복을 피하세요. 파일 이름은 도구 버전에 따라 다를 수 있으니, 에이전트에게 "네가 자동으로 읽는 규칙 파일 이름이 무엇인지" 물어보는 것이 가장 정확합니다.

### 4-1. 규칙 파일 작성 요청

```text
이 프로젝트의 에이전트 규칙 파일을 만들어 줘.
먼저 네가 세션 시작 시 자동으로 읽는 규칙 파일 이름을 알려 주고,
여러 에이전트가 함께 쓸 수 있도록 AGENTS.md에 본문을 쓰고 필요하면 네 전용 파일에서 참조해 줘.

포함할 내용:
1. 프로젝트 개요: 모바일 세로 이미지 검색 앱, Unity 버전, 렌더 파이프라인
2. 아키텍처 규칙
   - 레이어: Presentation → (Service) → Domain ← Data, Core는 공통
   - Domain(Model, Repository 인터페이스)은 UnityEngine과 DTO에 의존하지 않는다
   - DTO는 Data 레이어 밖으로 나가지 않고 Mapper로 Model로 바꾼다
   - 실패는 예외 대신 Result 패턴으로 돌려준다 (취소는 예외로 전파)
   - 레이어마다 Assembly Definition(asmdef)으로 의존 방향을 강제한다
3. 테스트 규칙
   - 새 기능은 테스트 시나리오를 먼저 합의하고 작성한다
   - Unit Test는 네트워크를 쓰지 않고 Mock만 쓴다
   - 테스트를 통과시키려고 테스트를 고치지 않는다. 테스트가 틀렸다면 근거를 먼저 보고한다
4. 작업 규칙
   - Unity 에디터 작업은 unity-cli 스킬로 하고, 씬/프리팹 파일을 직접 텍스트 편집하지 않는다
   - 완료 보고에는 컴파일 결과와 테스트 결과 요약을 포함한다
   - 커밋은 내가 요청할 때만 한다
5. 보안: API 키 등 비밀 값은 절대 커밋하지 않는다

작성 후 내용을 요약해서 보여 줘.
```

### ✅ 검토 포인트

- [ ] 규칙이 "좋은 코드를 써라" 같은 막연한 말이 아니라 **확인 가능한 문장**이다
- [ ] 의존 방향(Domain이 가장 안쪽)이 명확하다 — **DIP**
- [ ] 새 세션을 열고 "이 프로젝트의 아키텍처 규칙을 요약해 줘"라고 물었을 때 규칙 파일 내용으로 답한다

```text
규칙 파일을 커밋해 줘.
```

## 5. 디자인 분석 → PlantUML 클래스 다이어그램

이 단계가 교재의 핵심입니다. **화면(디자인)에서 출발해 데이터 구조와 클래스 설계를 끌어내는 과정**을 에이전트와 함께 합니다.

### 5-1. 디자인 전달

**방법 A. 글로 설명하기**

```text
만들 앱의 화면을 설명할게. 아직 코드는 쓰지 말고 분석만 해 줘.

[검색 화면]
- 상단: 검색어 입력창과 검색 버튼
- 본문: 검색 결과 이미지를 2열 그리드로 표시, 스크롤 가능
- 각 카드: 썸네일 이미지, 태그(쉼표로 구분), 작성자 이름
- 검색 중에는 "검색 중" 표시, 결과가 없으면 "결과 없음", 오류면 오류 메시지
〈[상세 화면] 등 원하는 화면이 더 있으면 추가〉
```

**방법 B. 스크린샷 붙여넣기**

참고하고 싶은 앱 화면이나 직접 그린 와이어프레임을 첨부합니다.

```text
첨부한 이미지는 내가 원하는 앱 화면이야. 아직 코드는 쓰지 말고 분석만 해 줘.
이미지에서 보이는 요소를 빠짐없이 나열하고, 보이지 않지만 필요할 것 같은 상태(로딩, 빈 결과, 오류)도 제안해 줘.
```

### 5-2. 화면 분석 요청

```text
위 화면을 분석해서 다음을 표로 정리해 줘.
1. 화면별 UI 요소
2. 사용자 행동(입력, 탭, 스크롤)과 그 결과
3. 화면에 표시하려면 필요한 데이터 항목 (예: 썸네일 URL, 태그, 작성자)
4. 화면 상태 (초기, 로딩, 성공, 빈 결과, 오류)

데이터 출처는 Pixabay 이미지 검색 API(https://pixabay.com/api/docs/)를 사용할 예정이야.
API 응답 필드 중 화면에 필요한 것만 골라 줘.
```

### 5-3. Model, Repository 도출과 Service 계층 판단

```text
분석 결과를 바탕으로 클래스 설계를 제안해 줘. 아직 코드는 쓰지 말고 설계만.

1. Model(Entity): 화면이 필요로 하는 데이터만 담은 클래스. API 응답 모양(DTO)과 분리해 줘.
2. Repository 인터페이스: 화면이 필요로 하는 기능을 메서드로. 반환 타입과 비동기/취소 처리 방식 포함.
3. Service(UseCase) 계층이 필요한지 판단해 줘.
   - 판단 근거를 "필요한 경우"와 "필요 없는 경우" 기준으로 설명하고
   - 이 앱의 현재 기능에서는 어느 쪽인지 결론을 내려 줘
   - 나중에 어떤 기능이 추가되면 Service가 필요해지는지도 알려 줘
4. 각 클래스가 어떤 SOLID 원칙과 관련되는지 한 줄씩.
```

> 💡 **Service 계층 판단 기준 (검토용)**
> - **필요한 경우:** 여러 Repository를 조합한다, 화면과 무관한 비즈니스 규칙(검색어 정규화, 금칙어, 최근 검색어 저장 등)이 있다, 여러 화면이 같은 로직을 공유한다
> - **필요 없는 경우:** Repository 메서드를 그대로 전달만 한다 → 불필요한 계층은 YAGNI 위반
> - 에이전트의 결론이 이 기준과 맞는지 확인하세요. 정답은 하나가 아니며, **근거가 타당한지**가 중요합니다.

### 5-4. PlantUML로 뽑아내기

```text
합의한 설계를 PlantUML 클래스 다이어그램으로 diagram.puml 파일에 작성해 줘.
- package로 레이어를 구분해 줘 (Core / Domain / 필요하면 Service)
- 이번에는 Domain까지만 그리고, Data 레이어는 다음 단계에서 추가할 거야
- 접근 제한자, 읽기 전용 속성, 생성자, 인터페이스/추상 클래스 표기를 정확히
- 관계(구현, 의존, 포함)에 짧은 설명 라벨을 붙여 줘
작성 후 문법 오류가 없는지 확인할 방법도 알려 줘.
```

PlantUML 확인 방법:

- JetBrains IDE(Rider 등) 또는 VS Code의 PlantUML 플러그인에서 미리보기
- [plantuml.com](https://www.plantuml.com/plantuml) 웹 서버에 붙여넣기
- 터미널: `plantuml diagram.puml` (Java와 PlantUML 설치 필요)

### ✅ 검토 포인트

- [ ] Model이 API 응답 필드명(`previewURL` 등)이 아니라 **앱에서 쓰기 좋은 이름**을 쓴다
- [ ] Model에 `UnityEngine` 타입(Texture2D 등)이 없다 → Domain의 순수성
- [ ] Repository는 **인터페이스**다 → DIP, 테스트에서 교체 가능
- [ ] 메서드 이름이 "무엇을 하는지"를 드러낸다 (예: 검색, 상세 조회)
- [ ] Service 계층 판단에 근거가 있다
- [ ] 다이어그램이 플러그인/웹에서 오류 없이 그려진다

```text
diagram.puml을 커밋해 줘.
```

## 6. 다이어그램 검토와 보강 (Result 패턴 등)

처음 설계에는 보통 "실패했을 때"가 빠져 있습니다. 이번 단계에서는 에이전트를 **리뷰어**로 써서 설계를 보강합니다.

### 6-1. 설계 리뷰 요청

```text
diagram.puml을 시니어 개발자 입장에서 리뷰해 줘. 수정은 아직 하지 말고 문제점과 제안만.
관점:
1. 실패 처리: 네트워크 오류, HTTP 오류(상태 코드), 결과 없음, 예상 못 한 오류, 사용자 취소를
   호출하는 쪽이 어떻게 구분할 수 있는가
2. SOLID: 특히 단일 책임(SRP), 의존 역전(DIP), 인터페이스 분리(ISP)
3. 테스트 용이성: Repository를 Mock으로 바꿔 끼울 수 있는가
4. 비동기: Unity에서 쓸 비동기 방식 선택지(async/await 라이브러리 등)와 장단점, 추천
```

### 6-2. Result 패턴과 에러 타입 보강

```text
리뷰 내용 중 다음을 반영해서 diagram.puml을 수정해 줘.
- Result<TData, TError> 타입: Discriminated Union(봉인된 레코드 계층) 형태의 불변 타입.
  - abstract record Result<TData, TError> 내부에 private 생성자를 두고
  - sealed record Success(TData data) : Result<TData, TError>
  - sealed record Error(TError error) : Result<TData, TError> 정의
- NetworkError enum 타입: 실패 원인을 명확한 열거형으로 정의
  (예: NetworkTimeout, ServerError, NotFound, Unknown, NoInternet 등)
- Repository 인터페이스: UniTask<Result<IReadOnlyList<ImageItem>, NetworkError>> 처럼
  반환 타입에 에러 enum을 명시하여 코드만 봐도 어떤 에러가 발생할지 아는 문서화 효과 부여
- Repository 메서드는 Result를 반환하고, 취소는 에러가 아니라 예외(OperationCanceledException)로 전파
- Result와 NetworkError는 Core 패키지에 두고 Domain이 참조
수정 후 변경된 부분을 요약해 줘.
```

### 6-3. Data 레이어 설계 추가

```text
이제 Data 레이어를 diagram.puml에 추가해 줘.
- DTO: Pixabay API 응답 JSON 모양 그대로
- DataSource 인터페이스: 원격 API 호출 담당. 실패 시 어떤 예외를 던지는지 명시
- DataSource 구현: 실제 HTTP 호출
- Mapper: DTO → Model 변환 (태그 문자열 "a, b, c"를 목록으로 바꾸는 규칙 포함)
- Repository 구현: DataSource를 호출하고, Mapper로 변환하고, 예외를 NetworkError enum으로 매핑하여 Result.Success 또는 Result.Error로 반환
의존 방향 화살표가 Data → Domain → Core로만 향하는지 확인해 줘.
```

### ✅ 검토 포인트

- [ ] 화면(Presentation)은 `Result`의 `Success` / `Error` 패턴 매칭으로 성공/실패를 깔끔하게 분기할 수 있다
- [ ] 예외 → `NetworkError` enum 매핑 책임이 **Repository 한 곳**에 있다 (SRP)
- [ ] Repository 시그니처만 보고도 발생 가능한 에러(`NetworkError`)를 명확히 파악할 수 있다 (코드 문서화)
- [ ] DTO는 Data 레이어 밖으로 나가지 않는다
- [ ] Mapper가 별도 클래스로 분리되어 **단독으로 테스트 가능**하다
- [ ] Domain에서 Data로 향하는 화살표가 없다 (DIP)
- [ ] 취소를 에러로 취급하지 않는 이유를 설명할 수 있다 (사용자가 새 검색을 하면 이전 검색은 취소되는 것이 정상 흐름)

```text
diagram.puml 변경을 커밋해 줘.
```

## 7. 주요 기능 테스트 시나리오 도출

코드를 쓰기 **전에** 무엇을 검증할지 합의합니다. 시나리오가 곧 요구사항 명세가 됩니다.

### 7-1. 시나리오 도출 요청

```text
diagram.puml의 Data 레이어와 Core를 기준으로 EditMode Unit Test 시나리오를 도출해 줘.
아직 코드는 쓰지 말고 표로만.

형식: 대상 클래스 | 시나리오 이름 | Given | When | Then
분류:
1. 정상 흐름 (검색 성공 → Result.Success<IReadOnlyList<ImageItem>> 반환)
2. 경계 값 (결과 0개, 빈 검색어, 공백만 있는 검색어, 태그가 비어 있음)
3. 실패 흐름 (HTTP 500 → NetworkError.ServerError, 404 → NetworkError.NotFound, 연결 실패 → NetworkError.NoInternet, 기타 예외 → NetworkError.Unknown)
4. 취소 (OperationCanceledException 예외 전파)
5. Mapper 단독 변환 규칙
6. Result<TData, TError> (Success, Error 레코드) 타입 자체의 규칙

그리고 테스트에 필요한 Mock 데이터(가짜 API 응답 JSON)와 Mock DataSource의 역할도 정리해 줘.
```

### 7-2. 시나리오 검토

```text
위 시나리오에서 빠진 경우가 있는지 스스로 점검해 줘.
특히 "빈 검색어일 때 DataSource를 아예 호출하지 않는다"처럼
호출 여부/호출 인자를 검증해야 하는 시나리오가 있는지 확인해 줘.
```

### ✅ 검토 포인트

- [ ] 모든 `NetworkError` enum 항목이 최소 한 번씩 등장한다
- [ ] Then이 "잘 동작한다"가 아니라 **확인 가능한 값**이다 (예: `result is Result<...>.Error { error: NetworkError.ServerError }`)
- [ ] 시나리오가 네트워크 없이 검증 가능하다
- [ ] Mock DataSource가 **응답 주입, 예외 주입, 호출 기록**을 할 수 있다

> 💡 합의한 시나리오 표를 `docs/test-scenarios.md` 같은 파일로 저장해 두라고 요청하면, 이후 단계에서 에이전트가 계속 참조할 수 있습니다.

## 8. Mock 데이터 기반 코드와 테스트 작성

### 8-1. 구현 계획 요청

```text
diagram.puml과 합의한 테스트 시나리오를 기준으로 Core, Domain, Data 레이어 코드와
EditMode 테스트를 작성할 거야. 먼저 계획만 보여 줘.
- 폴더와 파일 목록
- 레이어별 Assembly Definition(asmdef)과 참조 관계
- 필요한 패키지(비동기 라이브러리 등)와 설치 방법
- 테스트 어셈블리 구성, Mock 클래스 위치
```

### 8-2. 패키지 설치

비동기 라이브러리 등 패키지가 필요하면 스킬로 설치합니다.

```text
unity-package-management 스킬을 사용해서 계획한 패키지를 설치해 줘.
manifest.json을 직접 편집하지 말고 Package Manager API를 사용하고,
설치 후 manifest.json에 반영됐는지 확인해 줘.
```

### 8-3. 테스트 먼저, 그다음 구현

```text
계획대로 진행해 줘. 순서는 다음과 같이.
1. Core(Result<TData, TError>, NetworkError enum)와 Domain(Model, Repository 인터페이스) 작성
2. Mock 데이터(가짜 API 응답 JSON)와 Mock DataSource를 테스트 어셈블리에 작성
3. 합의한 시나리오대로 테스트 코드 작성
4. Data 레이어(DTO, DataSource, Mapper, Repository) 구현
5. 에디터에서 컴파일 에러가 없는지 확인

규칙:
- 테스트에서 실제 네트워크를 호출하지 않는다
- Mock은 테스트 어셈블리에만 둔다 (제품 코드에 섞지 않는다)
- 실제 HTTP DataSource는 URL 생성과 JSON 파싱처럼 네트워크 없이 검증할 수 있는 부분만 테스트한다
```

### ✅ 검토 포인트

- [ ] asmdef 참조가 설계한 의존 방향과 같다 (Domain asmdef가 Data를 참조하지 않음)
- [ ] Repository 구현이 생성자로 DataSource **인터페이스**를 받는다 (의존성 주입)
- [ ] Mock DataSource가 인터페이스를 구현한다 → **리스코프 치환(LSP)**: 진짜 대신 넣어도 Repository가 똑같이 동작
- [ ] Mapper가 null, 빈 문자열, 공백 태그를 처리한다
- [ ] 비밀 값(API 키)이 코드에 하드코딩되어 있지 않다 (생성자로 받음)

## 9. Unit Test 통과 확인

### 9-1. 테스트 실행

에디터를 열어 둔 상태와 닫은 상태에 따라 실행 방법이 다릅니다. 어느 쪽이든 에이전트가 알맞은 방법을 고르도록 요청합니다.

```text
unity-cli 스킬을 사용해서 EditMode 테스트를 실행하고 결과를 요약해 줘.
- 에디터가 열려 있으면 열린 에디터에서, 닫혀 있으면 배치 모드로 실행
- 전체/성공/실패 개수와, 실패한 테스트는 이름과 실패 메시지를 표로
```

참고로 CLI로 직접 실행하는 명령은 이렇습니다.

```bash
# 에디터가 닫혀 있을 때 (배치 모드)
unity test . --mode EditMode

# 에디터가 열려 있을 때 (Pipeline 패키지 필요)
unity command run_tests
```

## 11. UI와 데이터 연결

### 11-1. 연결 설계 확인

```text
검색 화면을 Repository와 연결하려고 해. 먼저 설계만 보여 줘.
- 화면 쪽이 Repository 인터페이스에만 의존하게 (구현 클래스를 직접 알지 않게)
- 구현 객체를 누가 만들어서 넣어 주는지 (Composition Root / 의존성 주입 방식)
- 검색 흐름: 입력 → 검색 중 표시 → Result 분기(Success(data), Error(error) 패턴 매칭 및 enum 종류별 메시지)
- 새 검색 시 이전 검색과 이미지 로딩 취소
- 썸네일 이미지 로딩과 메모리 해제
- 이 흐름을 diagram.puml에 Presentation 패키지로 추가해 줘
```

### 11-2. Mock 데이터로 실행 가능하게 연결

실제 API는 마지막에 연결합니다. 지금은 **실행할 수 있는 Mock 데이터 소스**를 만들어 앱을 돌려 봅니다.

```text
설계대로 화면과 데이터를 연결해 줘.
- 지금은 실제 API 대신 앱 실행용 Mock DataSource를 사용
- Mock은 Inspector에서 시나리오를 고를 수 있게: 성공 / 빈 결과 / 연결 실패 / 서버 오류
- Play 중에 시나리오를 바꾸면 다음 검색부터 적용
- Result.Error(error) 수신 시 NetworkError enum 종류별로 사용자에게 보여 줄 메시지를 다르게
완료 후 컴파일 확인, 기존 Unit Test 재실행, Play 모드에서 검색해 본 스크린샷을 보여 줘.
```

> 💡 **테스트용 Mock과 앱 실행용 Mock은 목적이 다릅니다.** 테스트용 Mock(8단계)은 호출 기록과 예외 주입이 목적이고 테스트 어셈블리에만 있습니다. 앱 실행용 Mock은 API 키 없이 앱을 돌려 보는 것이 목적이라 제품 코드에 들어갑니다.

### 11-3. 직접 확인

에디터에서 Play를 누르고 시나리오를 하나씩 바꿔 가며 검색해 봅니다.

| 시나리오 | 기대 화면 |
|---|---|
| 성공 | 카드 여러 개가 2열로 표시 |
| 빈 결과 | "결과 없음" 메시지 |
| 연결 실패 | 연결 확인 안내 메시지 |
| 서버 오류 | 서버 오류 메시지 (NetworkError.ServerError 매핑 확인) |

### ✅ 검토 포인트

- [ ] 화면 스크립트에 `new PixabayRemoteDataSource(...)`처럼 구현을 직접 만드는 코드가 **한 곳(Composition Root)에만** 있다
- [ ] 화면이 `try-catch`로 네트워크 예외를 잡지 않고 `Result`로 분기한다
- [ ] 검색을 빠르게 여러 번 해도 이전 결과가 섞이지 않는다 (취소 동작)
- [ ] 결과를 새로 표시할 때 이전 카드와 텍스처를 정리한다
- [ ] 기존 Unit Test가 여전히 모두 통과한다

## 12. PlayMode 테스트 시나리오 도출

Unit Test는 클래스 하나를 검증합니다. **PlayMode 테스트는 실제 씬에서 화면이 올바르게 반응하는지** 검증합니다.

### 12-1. 시나리오 도출 요청

```text
검색 화면의 PlayMode 테스트 시나리오를 도출해 줘. 아직 코드는 쓰지 말고 표로만.

형식: 시나리오 이름 | 준비(Mock 설정) | 사용자 행동 | 기대 화면 상태
포함할 것:
1. 첫 화면 상태 (안내 메시지, 결과 없음)
2. 검색 성공 → 카드 개수, 첫 카드의 텍스트
3. 빈 결과 → 결과 없음 메시지
4. 연결 실패 / 서버 오류 → 각각의 메시지
5. 빈 검색어로 검색 → 아무 요청도 하지 않음
6. 다시 검색 → 이전 카드가 사라지고 새 결과만 남음
7. 빠르게 두 번 검색 → 마지막 검색 결과만 표시

그리고 다음 설계 질문에 답해 줘.
- 테스트에서 Mock Repository를 화면에 어떻게 주입할지 (씬 로드 순서, 초기화 시점)
- 비동기 결과를 기다리는 방법 (고정 시간 대기를 피하는 방법)
- 실제 네트워크와 실제 API 키를 절대 쓰지 않도록 보장하는 방법
```

### ✅ 검토 포인트

- [ ] 기대 화면 상태가 **코드로 확인 가능**하다 (카드 개수, 텍스트 내용, 오브젝트 활성 여부)
- [ ] "몇 초 기다린 뒤 확인"이 아니라 **조건이 될 때까지 기다리는** 방식이다 (+ 타임아웃)
- [ ] Mock 주입 방식이 제품 코드를 테스트 때문에 크게 바꾸지 않는다
- [ ] 테스트끼리 영향을 주지 않는다 (각 테스트마다 씬을 새로 로드)

## 14. 실제 데이터 연결 (Pixabay)

모든 동작을 Mock으로 확인했으니 이제 실제 API를 연결합니다. 설계가 잘 되어 있다면 **DataSource 구현만 바꾸면** 됩니다 — 이것이 지금까지 인터페이스로 분리한 이유입니다 (**OCP, DIP**).

### 14-1. API 키 발급

1. [pixabay.com](https://pixabay.com)에 가입
2. [API 문서](https://pixabay.com/api/docs/)에서 로그인 상태로 자신의 API 키 확인

### 14-2. API 키 보안

API 키는 **비밀번호와 같습니다.** 한 번이라도 커밋하면 기록에 남기 때문에, 코드를 쓰기 전에 보관 방법부터 정합니다.

```text
Pixabay API 키를 안전하게 쓰는 방법을 제안해 줘. 아직 구현하지 마.
조건:
- 키가 Git에 절대 커밋되지 않을 것 (.gitignore로 보장)
- 키 파일이 없어도 앱이 실행될 것 (Mock으로 대체하고 경고 로그)
- 팀원이 자기 키를 넣는 방법을 README에 안내할 수 있을 것
그리고 모바일 앱에 키를 넣어 배포할 때의 위험과, 실제 서비스라면 어떻게 해야 하는지
(예: 키를 서버에 두고 앱은 서버를 호출) 짧게 설명해 줘.
```

선택한 방식으로 구현하고 확인합니다.

```text
제안한 방식으로 API 키 로딩을 구현해 줘.
구현 후 다음을 증명해 줘.
1. 키 파일을 만든 뒤 git status에 키 파일이 나타나지 않음
2. git check-ignore로 키 파일이 무시되는 규칙 확인
3. 지금까지의 커밋 기록에 키 문자열이 없음
```

### ✅ 보안 검토 포인트

- [ ] `git status`에 키 파일이 보이지 않는다
- [ ] 키 값이 코드, 씬, 프리팹, 로그 어디에도 없다
- [ ] 키가 없을 때 앱이 죽지 않고 Mock으로 동작한다
- [ ] (실수로 키를 커밋했다면) 키를 **즉시 재발급**했다 — 기록에서 지우는 것만으로는 부족

### 14-3. 실제 DataSource 연결

```text
실제 Pixabay DataSource를 앱에 연결해 줘.
- Pixabay API 문서의 요청 제한, 캐싱, 이미지 URL 사용 규칙을 확인해서 지켜야 할 점을 먼저 알려 줘
- API 키가 있으면 실제 DataSource, 없으면 앱 실행용 Mock을 사용
- Inspector에서 키가 있어도 Mock을 강제로 쓸 수 있는 옵션 유지 (오류 화면 확인용)
- Unit Test와 PlayMode 테스트는 계속 Mock만 사용
완료 후 모든 테스트를 실행하고, Play 모드에서 실제 검색어로 검색한 스크린샷을 보여 줘.
```

### 14-4. 실제 API 테스트는 따로

```text
실제 Pixabay API를 호출하는 통합 테스트를 1~2개 만들어 줘.
- 평소 테스트 실행에는 포함되지 않도록 (명시적으로 실행할 때만)
- 키가 없으면 실패가 아니라 건너뛰기(Ignore/Inconclusive)
```

### ✅ 검토 포인트

- [ ] 바뀐 파일이 대부분 **Data 레이어와 Composition Root**뿐이다 (Domain, Presentation은 거의 그대로)
- [ ] 실제 검색 결과의 썸네일이 표시된다
- [ ] 잘못된 키를 넣었을 때 앱이 죽지 않고 오류 메시지를 보여 준다
- [ ] 평소 테스트 실행은 여전히 네트워크 없이 통과한다

## 부록 A. 프롬프트 작성 템플릿

좋은 프롬프트에는 다섯 가지가 들어 있습니다.

```text
[목표]     무엇을 만들거나 바꾸는가
[맥락]     관련 파일, 이전 단계의 결정, 사용할 스킬
[제약]     하지 말아야 할 것, 지켜야 할 규칙
[완료 조건] 무엇이 확인되면 끝인가 (컴파일, 테스트, 스크린샷)
[보고 형식] 어떤 형태로 결과를 알려 줄 것인가 (표, 요약, 파일 목록)
```

예시:

```text
[목표] 검색 결과가 없을 때 안내 문구를 보여 줘.
[맥락] SearchController가 Result로 분기하고 있어. 규칙 파일의 아키텍처 규칙을 따라.
[제약] Repository와 Data 레이어는 건드리지 마.
[완료 조건] 컴파일 에러 없음, 기존 테스트 전부 통과, 빈 결과 시나리오로 Play한 스크린샷.
[보고 형식] 바꾼 파일 목록과 테스트 결과 요약.
```

### 상황별 짧은 프롬프트

| 상황 | 프롬프트 |
|---|---|
| 계획만 받고 싶을 때 | `아직 코드는 쓰지 말고 계획만 보여 줘.` |
| 선택지를 받고 싶을 때 | `선택지 2~3개를 장단점과 함께 보여 주고 추천을 알려 줘.` |
| 검토를 받고 싶을 때 | `시니어 개발자 입장에서 리뷰해 줘. 수정은 하지 말고 문제점만.` |
| 증거를 받고 싶을 때 | `됐다고만 하지 말고 테스트 결과와 스크린샷으로 보여 줘.` |
| 범위를 제한할 때 | `〈파일/레이어〉 외에는 수정하지 마.` |
| 되돌릴 때 | `마지막 커밋 이후 변경 사항을 보여 주고, 내가 고른 것만 되돌려 줘.` |
| 막혔을 때 | `같은 방법을 반복하지 말고 원인을 먼저 분석해서 보고해 줘.` |
