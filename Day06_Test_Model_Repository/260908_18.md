## Test 이론

클래스 개발은 절반 작성했더라도 실제로 완성까지는 4배 정도의 시간이 필요할 수 있다

테스트를 통해 실제 의도 대로 진행 되는지 확인 할 필요도 있다.

#### 테스트의 장점

- 장애에 관한 **신속한 피드백**
- 개발 주기에서 **조기 장애 감지**
- 회귀의 신경 쓸 필요 없이 코드를 최적화 하는 안전한 **코드 리펙터링**
- 기술적 문제를 최소화 하는 **안정적인 개발 속도**

#### 화이트 박스 테스트

- 내부 구조와 동작에 중점을 두고 테스트하는 방법
- 코드의 내부 로직, 제어 흐름, 데이터 흐름 등을 이해하고 검증하는 데에 사용
- 테스트 케이스를 설계할 때 코드의 특정 부분을 직접 확인
- 주요 기법으로는 구문 검사, 경로 검사, 조건/분기 검사 등이 있다

#### 블랙박스 테스트

- 소프트웨어의 내부 구조를 무시하고 기능을 테스트하는 방법
- 시스템이 어떻게 동작하는지에 대한 내부 정보를 알 필요 없이 사용자 관점에서 테스트
- 테스트 케이스는 입력 값과 예상 출력 값에 기반하여 설계
- 요구 사항을 충족하는지 확인하고, 시스템의 기능적 및 비기능적 요구 사항을 테스트
- 주요 기법으로는 등가 분할, 경계 값 분석, 상태 전이 테스트 등이 있다

#### 단위 테스트

특정 모듈이 의도한대로 작동 하는지를 테스트 하는 가장 작은 단위의 테스트 (메서드, 기능 등등)

- DB
    - 스키마가 변경되는 경우
    - 모델 클래스가 변경되는 경우
- Network
    - 네트워크 연결이 정상적인 경우
    - 네트워크 연결이 안 되었을 때
- 데이터 검증
    - 예측한 데이터를 제대로 처리하고 있는지
    - 잘못된 데이터가 들어올 경우

#### TDD(Test Driven Develoment)

테스트 중심으로 개발하는 방법론

테스트 코드를 먼저 작성하고 성공 하도록 코드를 수정

#### Test Double

테스트를 진행 하기 어려운 경우에 테스트가 가능하도록 만들어주는 객체

#### Mock 객체

Mock 객체(모의 객체)는 단위 테스트를 진행할 때, 실제 객체를 대체하기 위해 프로그래밍 방식으로 동작을 흉내 내는 가짜 객체

때때로 단위 테스트는 **서버나 DB**에서 데이터를 가져오는 클래스에 의존할 수 있다

이 경우 다음과 같은 몇 가지 이유로 불편하다

- 테스트 실행 속도가 느려진다
- 예기치 않은 결과를 반환하면 통과 테스트가 실패하기 시작할 수 있다.
- 가능한 모든 성공 및 실패 시나리오를 테스트하는 것은 어렵다
- 따라서 라이브 웹 서비스나 데이터베이스에 의존하는 대신 이러한 종속성을 Mocking할 수 있다.

Mock은 실제 구현 객체를 에뮬레이션하고 상황에 따라 특정 결과를 반환할 수 있다.

## Model, Repository

### **Model**

객체 클래스의 속성에 대한 데이터를 조회 가능한 클래스

별도의 기능을 가지지 않고 순수한 불변 객체로 작성이 일반적

데이터 구조 정의 \ 데이터 홀더 \ 직렬화 역직렬화를 가진다

### Repository 패턴

소프트웨어 개발에서 데이터 저장소에 접근하는 객체를 추상화 데이터 소스와의 통신을 담당하는 객체를 캡슐화 하는 디자인 패턴

책임과 역할

- **데이터 접근의 진입점**
- **데이터 접근에 대한 추상화 계층**
- 데이터 소스 은닉
- 비즈니스 로직과 데이터 소스 사이의 중재자
- 데이터 매핑, 변환 담당

리포지토리는 어떤 데이터르 제공할 것인 가를 집중한다

이점

- 관심사 분리
    - 게임의 핵심 로직과 데이터 저장 및 로딩 로직을 명확하게 분리
    - 예)플레이어 인벤토리 관리 : InventoryRepository
    - 테스트 용이성
        - 데이터 소스를 Mocking하여 단위 테스트를 쉽게 작성할 수 있음
        - 예)PlayerRepository를 테스트할 때 실제 서버 없이 가짜 데이터를 사용해 로직을 검증
    - 확장성
        - 새로운 데이터 저장 방식을 추가하기 용이
        - 예) 로컬 파일 저장 게임을 클라우드 저장소로 옮길 때

데이터 소스와 리포지터리

**리포지터리 패턴에서 데이터 소스**는 실제 데이터가 저장된 매체와 직접 소통하는 코드를 포함

**리포지토리**는 어떤 데이터를 제공할지에 초점을 맞추며, 데이터 소스를 사용하고 관리하는 역할

예시

- PlayerDataSource : 유저 데이터를 저장하거나 불러오는 로직을 담당
- PlayerRepository : PlayerDataSource를 사용하여 플레이어의 레벨, 경험치, 아이템 목록 등을 제공하는 메서드를 구현
- GetPlayerByLevel() 같은 게임 도메인 (비즈니스 문제 영역) 특화 쿼리를 포함할 수 있음

데이터 소스는 데이터를 읽고 쓰는 구체적인 메커니즘에 집중

용도에 맞는 저장 매체 특화 로직 구현이 가능하다

```csharp
using System.Collection.Generic;
using System.Treading.Tasks;

public interface IPlayerSource
{
	Task SavePlayer(Player player);
	Task<Player> LoadPlayer(string playerId);
	Task<List<Player>> LoadAllPlayers();
}
/*
- File 을 조작하거나
- 서버와 통신하거나
- 메모리를 사용하거나
- (옵션) 데이터 형식 변환

저장 매체와 직접적인 소통이 가능
*/
```

데이터 소스를 숨기고 상위 계층에서 일관된 방법으로 데이터에 저근하는 방식을 제공하여 데이터를 비즈니스 로직에 전달한다

도메인 특화 기능을 제공하고 장점도 있다

- 도메인 의도가 명확히 드러남
- 재사용 가능한 쿼리 로직
- 데이터 소스 구현과 분리된 비즈니스 요구사항 처리

주의사항

- Repository는 어떤 데이터를 전달할지에 집중
- Repository는 직접적인 데이터 조작이 아닌 필요한 데이터를 골라내는 일을 할 것
- 저장 매체를 다루는 코드는 DataSource 에서 하도록 할 것
