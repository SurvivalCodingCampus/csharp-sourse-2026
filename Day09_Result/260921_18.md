### 1. 기본 통신 아키텍처 & 데이터 흐름

#### Result

작업 성공과 실패 결과를 예외를 던지지 않고 하나의 객체로 명시적으로 반환하여 다루는 디자인 패턴

기존 try-catch가 가지는 문제

- 가독성 저하 (어떤 예외가 있는지 일일이 보거나 주석 설명에 의존)
- 흐름 제어의 어려움 (예외가 발생하면 호출 스택을 따라 예외가 상위로 전파 → 흐름 예측 어려움)
- 성능 비용 높음 (call stack 비용이 상대적으로 높음)

##### result 패턴

성공과 실패 중 하나를 리턴하는 Result 클래스

- Result 클래스는 성공시에는 데이터를, 실패시에는 에러 정보(예: Exception, String)를 담는 객체를 정의
- record 는 불변, 동등성 비교(Equals, HashCode), ToString 재정의 효과를 가지는 class 의 형태
- sealed calss의 다른 특징
   - sealed를 클래스나 메서드에 붙이면 붙이면 상속 이나 오버라이드가 금지
   - sealed class 는 서브타입을 봉인하는 클래스
   - sealed class 는 패턴매칭을 활용하여 모든 서브타입에 대한 처리를 하기 용이
   - sealed 클래스는 타입 봉인 효과를 가진다 (enum 하고 비슷한 효과 + 다른 객체의 참조를 가짐)
   - 타입 안정성 향상, 명확한 분기 처리, 에러 처리 누락 방지 유도에 장점이 있음
- Result 패턴은 여러가지 종류의 성공과 실패를 처리하기 용이한 패턴
- 코드만 봐도 어떤 에러가 발생할지 미리 알수 있어서 코드가 문서화 가능

```csharp

	Task<Result<Models.Pokemon, PokemonError>> GetPokemonByNameAsync(string pokemonName)
}
```

### 최종 HTTP 통신 구조

- **Data**
    - Common : result 패턴으로 에러 확인
        - Errors
    - DataSource : 데이터를 접근
    - DTOs : 데이터를 받아옴
    - Mapper : 받은 데이터를 모델로 이동(역직렬화)
    - Models : 필요한 데이터만 받아옴
    - Repositories : 데이터 정리

* **Remote DB:** 원본 데이터 저장소
* **DataSource:** HttpClient 기반 데이터 수신 및 단순 역직렬화
* **DTO:** 서버의 JSON 구조를 그대로 받아내는 중간 객체
* **Mapper:** DTO를 앱 안전한 Model로 변환하는 유틸리티
* **Model:** 앱 내부에서 실제 사용하는 **Non-nullable** 중심 도메인 객체
* **Repository:** 데이터 가공, 분류 및 비즈니스 로직 처리
