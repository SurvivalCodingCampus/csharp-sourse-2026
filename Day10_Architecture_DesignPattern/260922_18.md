### 설계 원칙, 디자인 패턴

#### 설계 원칙

응집도 (Cohesion)

- 모듈이 하나의 목적을 수행하는 요소들간의 연관성 척도
- 모듈 내부의 기능적인 응집 정도를 나타냄

결합도 (Coupling)

- 모듈이 다른 모듈에 의존하는 정도의 척도
- 모듈과 모듈간의 상호 결합 정도를 나타냄
- **높은 응집도** : 모듈이 하나의 특정 작업이나 기능에 집중
  - UserAuthentication 클래스 : 로그인, 로그아웃, 비밀번호 변경 기능
- 낮은 응집도 : 모듈이 여러 가지 서로 관련 없는 작업을 수행
  - Util 클래스 : 문자열 처리, 파일 읽기, 날짜 계산 기능
- **낮은 결합도** : 모듈이 서로 독립적으로 작동할 수 있을 때
  - UserAuthentication 클래스가 특정 클래스가 아니라 인터페이스를 통해 사용자 정보를 가져오는 경우
- 높은 결합도 : 모듈이 서로 강하게 연결되어 있을 때
  - UserAuthentication 클래스가 특정 클래스의 내부 구현에 직접 의존하는 경우

코드 작성 원칙

- DRY - Don’t Repeat Yourself : 같은 것을 몇번씩 반복하지 말라

  • 중복 코드가 있다면 메소드로 분리한다

- PIE - Program Intently and Expressively : 명확하고 표현력 있게 기술하자
  - 애매한 이름은 쓰기 금지
  - 알기 쉬운 이름을 쓰기
  - 컨벤션을 따르자
  - 매직 넘버에 이름을 붙이기
- SRP - Single Responsibility Principle : 클래스에 주어진 책임은 1개뿐
  - 단일 책임 원칙
  - 1개의 클래스는 1개의 일만 수행
  - 한 부분의 에러를 수정하기 위해서는 그 클래스만 수정
  - 하지만 클래스 분리가 심해지면 오히려 관리가 어려움
- OCP - Open Closed Principle : 개방 폐쇄 원칙(원본 코드를 수정없이 새로운 기능을 추가 가능)
  - 확장에 대해서는 열려있고 (확장은 자유롭고), 변경에 대해서는 닫혀있음 (의존 부분의 변경은 불필요)
  - 수정 없이 확장 가능이 목표
  - Iterable, Comparator 등이 좋은 예
  - String 의 경우는 상속 금지이므로 OCP에 반하는 클래스의 대표적인 예.
  - 인터페이스를 적극 활용하여 확장
- SDP - Stable Dependencies Principle : 안전한 것에 의존하라
  - ATM 시스템을 예를 들면 암호 처리 같이 한번 완성되면 수정될 가능성이 없는 클래스에 의존
  - 가장 좋은 것은 특정 클래스가 아니라 인터페이스에 의존
  - 클래스는 생성자가 변할수 있지만 인터페이스는 그대로임
  - 안전한 것에 의존
- ADP - 의존성 비순환 원칙
  - 의존성 비순환 원칙
  - 의존 관계에 사이클이 발생되지 않게 함
- SOLID 원칙
  - S : SRP 단일 책임 원칙 한 클래스는 하나의 책임만
  - O : OCP 개방-폐쇄 원칙 확장엔 열려있지만 변경에는 폐쇄적
  - L : LSP 리스코프 치환원칙 계약의 의한 설계(객체는 정확성을 꺠뜨리지 않고 하위타입의 인스턴스로 바꿀수 있어야 함)
  - I : ISP 인터페이스 분리 원칙 특정 클라이언트를 위한 인터페이스 여러 개가 효율적 (범용 보다 나음)
  - D : DIP 의존관계 역전 원칙 추상화에 의존 O 구체화에 의존 X (의존성 주입의 기본)

#### 디자인 패턴

소프트웨어 디자인 패턴(software design pattern)은 소프트웨어 공학의 소프트웨어 디자인에서 특정 문맥에서 공통적으로 발생하는 문제에 대해 재사용 가능한 해결책이다.

디자인 패턴은 프로그래머가 어플리케이션이나 시스템을 디자인할 때 공통된 문제들을 해결하는데에 쓰이는 형식화 된 가장 좋은 관행이다.

톱니바퀴를 발명 하지 말라

**디자인 패턴을 공부했을 때의 장점**

- 개발자간에 커뮤니케이션이 원만
- 객체지향 설계 원칙의 이해도 증가
- Update() 지옥, 거대 객체 방지 : 상태 패턴 적용하여 SRP, OCP 를 지킬 수 있음
  - Update() 내부에 수많은 if-else 방지
- 잦은 기획 변경, 신규 콘텐츠 확장에 대응 : 팩토리, 전략 패턴
  - 새로운 스킬 추가, 보스 패턴 변경 대응
- 시스템 간 결합도 최소화 : 옵저버, 이벤트 드리븐 패턴
  - 플레이어 사망시 UI 갱신, 사망 사운드 재생, 업적 달성

***GoF의 23가지 디자인 패턴***

Gang Of Four 라는 4명의 개발자가 정리한 디자인 패턴

사실상 지금까지 디자인 패턴이라고 부르는 것은 다 여기서 나옴

- 생성(Creational) 패턴
  - 추상 팩토리
  - 빌더
    - 빌더 패턴은 복잡한 객체를 단계적으로 생성하는 데 유용 (StringBuffer)
  - 팩토리 메서드

    Factory 패턴 : 인스턴스를 만드는 패턴

  - 프로토타입
  - 싱글턴

    1개의 인스턴스만 생성되는 것을 보증하기 위한 패턴

    인스턴스 생성을 여러번 시도해도 1개의 인스턴스가 공유됨

    캐시나 공유 데이터, 처리의 효율화 등에 사용되는 테크닉

- 구조(Structual) 패턴
  - 어뎁터
  - 브리지
  - 컴퍼지트
  - 데커레이터
  - 파사드

    내부를 감추고 심플하게 (http 패키지)

    - 복잡한 하위 시스템을 단순화 하기 위한 패턴
    - 이사를 가면 주소를 변경할 때, 주민센터, 카드회사, 학교 등에 알려야 한다. 이를 하나하나 일일이 하는 것은 매우 귀찮기 때문에 한번에 해 주는 서비스가 있다면 그것을 이용하면 된다는 이론
  - 플라이웨이트
  - 프록시
- 행위(Behavioral) 패턴
  - 책임 연쇄
  - 커맨드
  - 인터프리터
  - 이터레이터

    반복 구조 (IEnumerable)

  - 미디에이터
  - 메멘토
  - 옵저버

    주로 분산 이벤트 핸들링 시스템을 구현하는 데 사용 발행/구독 모델로 알려져 있음

    대표적으로 콜백 함수 존재

  - 테이트
  - 스트래티지

    전략 패턴 - 갈아 끼우기(**런타임**에 알고리즘을 동적으로 교체할 수 있도록)

  - 탬플릿메서드
  - 비지터

**Service - 규칙을 지키는 계층**

화면을 모르는 채로, 비즈니스 규칙을 적용하고 결과를 돌려주는 계층

1. 입력 검증 (빈 이름 거르기)
2. 규칙 적용 (전설 포켓몬 조회 제한)
3. 여러 Repository 조합 (미네랄 + 가스 + 인구수를 함께 확인)

## 📷 실행 결과 (또는 테스트 결과)
**과제 2 Model 및 Repository 설계와 비교하여, Service를 도입했을 때 구조적으로 달라지는 부분과 책임 분리 효과를 설명해 줘**

- 가장 큰 변화는 사용자 행동 하나를 완성하는 책임이 명시적인 계층으로 이동한다는 것입니다.

- Service가 없으면 “작업 완료” 과정이 UI나 Repository에 들어가기 쉽습니다.

- 플레이어 조회
→ 작업 조회
→ 열쇠 확인
→ 열쇠 차감
→ 작업 완료
→ 건물 업그레이드
→ 구역 진행도 반영
→ 저장

- Service를 도입하면 UI는 다음 요청만 전달하면 됩니다.
```
TaskService.completeTask(playerId, taskId)
```

**과제 3**
- SRP (단일 책임)
  - 과제 1의 Repository에 데이터 통신 외의 비즈니스 로직이나 데이터 가공 코드가 섞여 있었는지 확인하고, 과제 2에서 Service가 추가되면서 책임이 어떻게 분리되었는지 비교
- DIP / SDP (의존성 원칙)
   - 구현 클래스에 직접 의존하는 부분이 남아있는지, 인터페이스를 통해 결합도가 낮아졌는지 검토
- 에러 처리 : Result 패턴 누락 여부
- 구조적 변경에 따른 트레이드오프
   - 계층 분리로 인해 코드가 복잡해진 부분은 없는지, 유지보수 관점에서 어떤 이점이 생겼는지 정리
